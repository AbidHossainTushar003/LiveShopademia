## Filesystem race boundary and required ownership model — 2026-10-14

The path guard verifies the canonical path and then delegates a pathname to `express.static`, which opens the path separately. This remains a TOCTOU race if an actor can replace path components. The disposable junction test demonstrates only out-of-root junction rejection at check time; it does not demonstrate race resistance. Node's current cross-platform Express pathname-serving path does not bind the checked file handle to the later open. No stronger guarantee or concurrent-race pass is claimed.

Before hosting:

1. Make the release tree, all parents, and `css`, `js`, `admin-assets`, and `public-assets` owned by a separate deployment/release principal. The application runtime principal gets read/traverse only (POSIX `r-x`; Windows Read & Execute), with no directory-entry create, replace, rename, delete, or ACL-change rights. Updates use a separately authorized immutable release tree/switch.
2. Keep uploads outside the code/static release tree. Do not serve an app-writable ingestion directory directly. Prefer app-only write access to a separate ingestion/quarantine directory and an authorized validation/publish step into immutable content-addressed published storage that the serving runtime mounts read-only.
3. Prevent untrusted users from creating symlinks/junctions/reparse points in any serving path. Apply supported mount restrictions (`noexec,nodev,nosuid` to writable data where compatible) and retain paired upload/DB backup coverage.
4. Capture actual runtime UID/SID, owner/group/ACL, parent-directory rights, mount/storage identities and app-vs-publisher write tests as evidence. Acceptance requires proving the runtime cannot mutate any served asset tree and that only the intended ingestion identity writes unserved uploads. If this separation cannot be enforced, the race gate remains **BLOCKED** unless platform-specific handle-relative serving is implemented and race-tested on the actual OS.

The existing project may have application upload handlers that write to the same upload directory served by Express. Therefore these deployment constraints are a required architecture/hosting gate, not a claim that current runtime permissions already meet it. Do not assign those identities or change the local preview as part of this audit.

## 4. Pre-deployment and backup sequence

## 7. Recovery and rollback

- Stop rollout and preserve logs if health, migration, permissions, or smoke checks fail.
- Do not automatically reverse a schema or restore over a live database. Use only the pre-reviewed, target-specific forward-repair or isolated restore procedure approved for that release.
- Application rollback and database recovery are separate decisions. A code rollback is appropriate only if the prior app release is compatible with the already-applied schema and data. The current cPanel deploy is an in-place `rsync --delete`; it has no release-directory switch or built-in rollback. Before any authorized deployment, preserve an access-controlled copy of the exact prior app release and dependency lock/config references, and rehearse restoration/switch-back on staging. Exclude `.env`, uploads, and database data from code rollback; retain these under their independent recovery procedures.
- For database changes, prefer reviewed additive/expand-contract migrations that keep old and new app versions compatible. If migration failure or incompatible data is suspected, stop writes/rollout, preserve logs, and use only the release-specific reviewed forward repair or restore of a verified backup into an isolated database. Do not blindly run down migrations or restore over the live database. Any production database switch/restore requires separate explicit authorization.
- Preserve the failed release identifier, migration IDs/checksums, timestamps, relevant redacted logs, and backup pair. Avoid copying customer or secret values into incident notes.
- Restore to an isolated target first; compare integrity and confirm the chosen recovery point before an authorized operator makes any production switch.
- Record recovery duration, data-loss window, integrity checks, and follow-up actions. Reopen launch only after the owner reviews the evidence.
